# 02 — UX: every screen

The behaviour of each screen: what it is for, what is on it, every state it can
be in, the words it uses, and how it is operated. Visual rules are in
`03-design-system.md`. Section numbers are referenced from the code and from
`11-build-plan.md`; do not renumber.

For each screen, "Built" means the file exists in `reference/mobile` and works;
"To build" means it is specified here and the plan has a step for it. For
every screen to build there is a web implementation in this repository to port
the logic from — it is named in the section.

## 1. Principles

1. **Answer first.** Every screen opens on the answer to the question that
   brought the person there, not on navigation or chrome.
2. **One thumb.** Primary actions sit in the lower half of the screen. Nothing
   important is only reachable at the top corners.
3. **Plain words.** "In range", "Borderline", "High", "Low". Never "abnormal",
   "critical", "risk", "optimal", "score". Dates are written out: `18 Sep 2026`.
4. **Calm.** Status colour appears only on results. No red banners, no badges
   on the app icon, no exclamation marks.
5. **Never lose what was typed.** A failed save keeps the form exactly as it
   was and says what happened.
6. **Readable at arm's length.** Body text is 17pt and follows Dynamic Type.
   Minimum text size 12pt. Minimum touch target 44×44pt.
7. **Works without signal for reading.** The last-seen data opens instantly
   from the on-device cache. Writing needs a connection and says so.

## 2. Navigation map

```
Root stack
├─ (auth)                         signed out only
│   ├─ index        Sign in                              Built
│   └─ verify       Six-digit code                       Built
├─ auth/callback    redirect target for Google           Built
└─ (app)                          signed in only
    ├─ onboarding   First profile (only while none exists)   Built
    ├─ (tabs)       system tab bar
    │   ├─ index     Overview                            Built
    │   ├─ markers   Markers                             To build  §5
    │   ├─ timeline  Timeline                            To build  §7
    │   └─ settings  Settings                            Built (profiles + custom markers: to build §9)
    ├─ marker/[id]   Marker detail (push)                Built (own range + delete result: to build §8)
    ├─ add-results   Add results (modal sheet)           To build  §6
    ├─ paywall       bbiom Pro (modal sheet)             Built
    └─ summary       Doctor summary (push, Pro)          To build  §11
```

Rules:

- **Four tabs.** Adding results is an action, not a place: it is the button in
  the Overview header and the primary button on every empty state, and it opens
  as a modal sheet over whatever is showing.
- Routes are protected in the layouts (`Stack.Protected`), so a signed-out
  person cannot reach `(app)` by a link, and an account with no profile can
  reach only `onboarding`.
- Back is always the system back gesture and the system back button. No custom
  back affordances.
- The active profile is remembered on the device and applies to every tab.

## 3. Sign in — `(auth)/index`, `(auth)/verify` · Built

**Job:** get a new or returning person into their record with as little typing
as possible.

One screen serves sign-in and sign-up; the same actions create the account.

Layout, top to bottom:

- Upper two-thirds: the painted panel (`hero`, flipped so green sits behind the
  type) with the kicker "Blood test tracker" and the headline "Every blood test
  you've had, on one clear timeline."
- Lower sheet on paper:
  1. **Continue with Apple** — the system button, black, full width.
  2. Divider "or use your email".
  3. Email field (email keyboard, no autocapitalise, autofill `emailAddress`).
  4. **Email me a code** — secondary. Disabled until the field looks like an email.
  5. **Continue with Google** — text button.
  6. One line: "bbiom tracks values you enter and does not provide medical
     advice. Discuss results with your healthcare provider."

Code screen (`verify`): kicker "Check your email", title "Enter the six-digit
code", the address it was sent to, one large numeric field with
`textContentType="oneTimeCode"` so iOS offers the code from Mail. The code
submits itself on the sixth digit. Below: **Send a new code** (once, then reads
"New code sent") and **Use a different email**.

States and copy:

| Situation | Behaviour |
| --- | --- |
| Apple or Google sheet dismissed | Nothing. Not an error. |
| Email could not be sent | "We could not send a code to that address. Check it and try again." |
| Wrong or expired code | Field clears. "That code is not right, or it has expired. Check the latest email, or send a new code." |
| Asked for a new code too soon (60 s limit) | "We could not send a new code yet. Wait a minute and try again." |
| Success | No message. The root layout swaps to the app the instant a session exists. |

No passwords exist anywhere in the product.

## 3a. First profile — `(app)/onboarding` · Built

Shown once, when the account has no profile. Kicker "One quick step", title
"Who are these results for?", one sentence on why sex is asked ("lets bbiom
pick the right standard range where it differs"), a name field (default
suggestion "Me"), three choices for sex (Female / Male / Prefer not to say —
stored as `F` / `M` / `OTHER`), and **Continue**. Date of birth is not asked
here; it can be added in Settings.

## 4. Overview — `(tabs)/index` · Built

**Job:** "How am I doing?" answered without scrolling.

Top to bottom:

1. **Header.** Title "Overview"; under it `{name} · last test {date} · {n}
   months ago`. On the right, the **Add** button (opens §6).
2. **Profile chips** — only if the account has more than one profile.
   Horizontal, the active one filled. One tap switches everything.
3. **Summary card.** "Latest result for each marker", then the one large
   figure: `17` "of 22 markers in range". A thin proportional bar (in range /
   borderline / out / no range, 2pt gaps), then three rows: In range,
   Borderline, Out of range, each with its shape and count.
4. **Worth a closer look** (count). A full card per marker that is out of range
   or borderline on its latest test, out-of-range first, then by how far
   outside. Each card: name, body system, status chip, the reading with its
   unit, a sparkline, the range bar with its limits printed, and "↑ 3 mg/dL
   since 4 Nov 2025 · 9 results". If none: one quiet line, "Every marker with a
   reference range is inside it on its latest test."
5. **Watching** (count) — pinned markers that are *not* already in the section
   above, as compact rows.
6. **By body system.** One card per system that has results: name, marker
   count, a row of status shapes (one per marker), and a note: "All in range"
   or "1 out of range · 2 borderline". Tapping opens Markers filtered to that
   system.

Pull down to refresh.

States:

| State | What shows |
| --- | --- |
| Loading, nothing cached | Centered spinner on paper |
| Offline with cache | The cached screen, unchanged. No banner. |
| Error, nothing cached | "We could not load this just now. Check your connection and try again." + **Try again** |
| No tests yet | Full-height painted panel: kicker "First entry", "Start {name}'s record with any report", two sentences, **Add your first results** |

## 5. Markers — `(tabs)/markers` · To build

**Job:** find any marker fast, by the name printed on the report.

Port from: `src/components/biomarkers/biomarker-browser.tsx` and
`src/components/views/markers-view.tsx`.

- **Header.** Title "Markers".
- **Search field** pinned under the header: "Search by name or abbreviation —
  LDL, A1c, TSH". Matches `name` and every entry in `aliases`,
  case-insensitively, as you type.
- **Scope control** (segmented, three options): **With results** (default when
  the profile has any results) · **Worth a look** · **Whole catalog** (default
  when it has none).
- **List**, grouped by body system in this order: Glucose & Metabolic, Lipids,
  Complete Blood Count, Liver, Kidney & Electrolytes, Thyroid, Iron Studies,
  Vitamins, Hormones, Other & Inflammation. Section header: system name and
  count. Within a section, most-ordered markers first (`MARKER_RANK` in
  `src/lib/commonality.ts`), then alphabetical.
- **Row** (`MarkerRow`): name; under it "18 Sep 2026 · 9 results" or "No
  results yet"; on the right the value with unit and a shape + word for status.
  Rows without results show "Add a result" and open marker detail.
- A route param `system` (from the Overview's body-system cards) scrolls to
  that section and selects **With results**.
- Use a `SectionList`; the catalog is 71 rows plus custom markers.

States: empty search → "No markers match. Try the whole catalog or a different
spelling." Empty "Worth a look" → "Nothing is outside or near a limit on its
latest test."

## 6. Add results — `add-results` (modal) · To build

**Job:** a 20-marker report entered in about three minutes, without a mistake
that silently corrupts the record. This is the hardest screen and the one that
decides whether people come back.

Port from: `src/components/sessions/new-session-form.tsx` (form logic) and
`createSession` in `src/app/app/actions.ts` (validation, unit conversion,
plausibility, duplicate check). Save through `api.createSession()`.

### Flow: one sheet, three parts

**Part A — About this test**

- **Date** (required). Defaults to today. A native date picker, `maximumDate`
  = today. This is the collection date printed on the report.
- **Lab name** (optional). Suggest the most recent lab name for this profile as
  a one-tap chip above the field.
- **Fasting** (switch). **Notes** (optional, multi-line, 2000 max).
- "Ordered by" is omitted on the phone (it exists on the web; send `null`).

**Part B — Which markers**

- **Panel shortcuts** as wrapping chips: Lipid Panel, Complete Blood Count,
  Comprehensive Metabolic, Thyroid Panel, HbA1c, Vitamin D, Iron Studies, Liver
  Panel (`PANELS` from `@domain`). Tapping adds that panel's rows that are not
  already present. A panel whose rows are all present shows a check.
- **Add a single marker**: a search field with results underneath (same
  matching as §5), tapping adds one row.

**Part C — Results**

One row per marker, in the order added:

```
LDL Cholesterol                               ×
usual range under 100 mg/dL
[ 94      ]   [ mg/dL ▾ ]
Range on report (optional)   [ min ] – [ max ]
```

- **Value field:** `keyboardType="decimal-pad"`, right-aligned, tabular
  figures. Accept both `.` and `,` as the decimal separator (`parseDecimal`
  from `@domain`). "Next" on the keyboard moves to the next row's value field —
  this single behaviour is most of the three-minute target. Use an input
  accessory or `returnKeyType="next"` with refs.
- **Unit:** a menu when the marker has alternatives (`altUnits`), plain text
  when it has one. Defaults to the unit the person last used for that marker
  (their display-unit preference), else the canonical unit.
- **Range on report:** two small optional fields, collapsed behind "Add the
  range from your report" until tapped, so the common case stays one field per
  marker. In the unit selected for that row.
- **×** removes the row.
- Empty rows are simply not saved. Only the date is required.

**Footer, pinned above the keyboard:** primary button **Save test · N
results**. Disabled while a value is not a number; then a line under it: "Some
values are not numbers yet."

### Checks before saving — run on the device, in this order

1. **Convert.** Each value and each entered range is converted to the marker's
   canonical unit with `toCanonical` / `conversionFactor` from `@domain`. The
   database stores canonical values only.
2. **Plausibility** (`checkPlausibility` from `@domain`). A value outside
   0.05×–20× of the range midpoint is almost always a slipped decimal or the
   wrong unit. For each such row show a sheet:

   > **Double-check these values**
   > LDL Cholesterol: 2.4 mg/dL looks unusual. Did you mean **2.4 mmol/L (= 93 mg/dL)**?
   > [Use mmol/L] [The value is correct] [Let me edit]

   "Use …" switches that row's unit. "The value is correct" marks the row
   confirmed and continues. Never block: a real result can be extreme.
3. **Duplicates.** If a result for the same marker already exists on the same
   date for this profile (check the cached record), warn once: "LDL Cholesterol
   already has a value on this date. Saving will add a second entry." [Save
   anyway] [Let me edit].
4. **Save** with one call to `api.createSession()` (one database transaction).

### After saving

Dismiss the sheet, refresh the record, return to where the person was. No
success screen. A light success haptic.

### Errors

| `ApiError.code` | Message | Then |
| --- | --- | --- |
| `session_limit` | "The Free plan includes 20 tests. Your 20 are all still here and readable. Pro removes the limit." | Buttons: **See Pro** (opens §10, keeps the form), **Not now** |
| `date_in_future` | "That date is in the future. Check the collection date." | Focus the date |
| `request_failed` (offline or server) | "Not saved. You appear to be offline, and nothing was lost — try again when you have signal." | Form stays exactly as it was |

Dismissing a sheet that has typed values asks: "Discard this test?" [Keep
editing] [Discard].

## 7. Timeline — `(tabs)/timeline` · To build

**Job:** the record in the order it happened, with the reasons beside it.

Port from: `src/components/views/timeline-view.tsx`.

- **Header.** Title "Timeline"; subtitle `{name} · 10 tests · 3 life events`.
  A **+** button opens "Add a life event".
- **List**, newest first, grouped by year (year as a sticky section header).
  Two kinds of entry on one vertical rail:
  - **Test** — a card: date (headline), `{lab} · fasting · 22 results`, and on
    the right the tallies as shape + number (▲ 2 ◆ 3) or "all in range".
    Tapping expands it in place to its results: flagged first, then
    alphabetical; each line is name, value + unit, status. Tapping a line opens
    that marker. One test open at a time. The newest starts open.
  - **Life event** — a single line on the rail: date, label.
- **Add a life event** (small sheet): date (default today), "What happened"
  (120 max, placeholder "Started vitamin D 2000 IU"), **Add event**.
- **Deleting** is by swipe-to-delete on a life event, and from a "Delete this
  test…" row at the bottom of an expanded test. Both confirm first: "Delete
  this test and its 22 results? This cannot be undone." Deleting is not
  available offline.

Empty state: "Nothing here yet. Your first test will appear as soon as you add
it." + **Add results**.

## 8. Marker detail — `marker/[id]` · Built, with two parts to build

**Job:** one marker, start to finish — where it is now, where it has been, and
against what.

Built:

- Title (marker name) and a **Watch / Watching** toggle that pins it to the
  Overview.
- **Unit switch** when the marker has more than one unit. The choice is saved
  per account and applies everywhere.
- **The chart card** (`MarkerChart`): the reading block (date line, the large
  value with unit, status chip, change since the previous test, the reference
  used), the range bar, a time-window control (1Y / 3Y / 5Y / All, counted back
  from the latest test), then the line: range band shaded, each test a point in
  its status shape, life events as labelled rules, legend underneath.
  **Dragging a finger across the chart** moves the reading block to that test,
  with a selection haptic per point; lifting returns to the latest.
- **History**: every result, newest first — date, lab, value, change, status.
  This list is the chart's text equivalent for VoiceOver.

To build (port from `src/components/views/marker-detail-view.tsx`):

- **Reference range card** below the history: the range in use, one sentence —
  "A range printed on a specific report always wins for that result, then your
  own range, then the catalog default." — and **Set your own range**: two
  optional numeric fields (min, max) in the display unit, **Save range**, and
  "Leave both blank and save to clear it." Validate min ≤ max ("The minimum
  must be less than or equal to the maximum."). Save with
  `api.setCustomRange()` (convert to canonical first).
- **Delete a result**: swipe a history row → "Delete this result?" →
  `api.deleteResult()`.
- When the profile's sex is "Prefer not to say" and the catalog range differs
  by sex (`summary.ambiguousSex`), show the note: "The typical range for this
  marker differs by sex. A result is only judged when the range from your own
  lab report is entered with it."

A marker with no results shows "No results recorded for {name} yet." and an
**Add results** button.

## 9. Settings — `(tabs)/settings` · Built, with two parts to build

Built, in this order:

1. **Header**: "Settings" and the account email (or "Signed in with Apple").
2. **Plan** card: Free ("1 profile · 12 of 20 tests used · export always
   included") with **See Pro**; or Pro with the renewal or end date and, for an
   App Store subscription, **Manage subscription** (opens Apple's sheet). A
   subscription bought on the website says so and is managed there.
3. **Privacy**: "Require Face ID" switch. Turning it on or off itself asks for
   Face ID. Disabled with an explanation if the phone has no biometrics or
   passcode set.
4. **Your data**: **Export as CSV**, **Export as JSON** (share sheet). One line:
   "Export and deletion are free on every plan. Your health data is yours."
5. **About**: Privacy policy, Terms of use, Help and support — each opens in
   an in-app browser. URLs are in `lib/links.ts` (shared with the paywall).
6. **Sign out**; **Delete account** (destructive style).
7. The disclaimer, in full.

Delete account: an alert — "Delete your account? This permanently removes every
profile, test, result and note, and your sign-in. There is no undo. Export your
data first if you want a copy." [Cancel] [Delete everything]. For Apple
accounts the system Apple sheet appears once more (needed to revoke the Apple
sign-in grant). If an App Store subscription is still renewing, a second alert
after deletion: "Your account is deleted. Your App Store subscription is billed
by Apple and is still active: cancel it in Settings › Apple Account ›
Subscriptions."

To build (port from `src/app/app/settings/page.tsx`), inserted after Plan:

- **Profiles**: a row per profile (name, sex, date of birth) that opens an edit
  sheet; **Add a family member** when under the plan's limit, otherwise the
  line "The Free plan includes one profile. Pro adds up to six." with **See
  Pro**. Handle `profile_limit` from the database the same way.
- **Custom markers**: list of the account's own markers; **New custom marker**
  sheet (name, unit, body system, optional range min / max). A marker with
  results is archived, never deleted.
- **Doctor summary** row (Pro) → §11. On Free it reads "Doctor summary · Pro"
  and opens the paywall.

## 10. Paywall — `paywall` (modal) · Built

**Job:** an honest offer, once, with everything App Review requires visible
without scrolling on a current iPhone.

- Full-height dark-green painted panel; **Close** top right, always.
- Kicker "bbiom Pro"; title "For the appointment, and for the people you look
  after."
- A glass card with the three things Pro adds, and the line "Tracking, trends,
  ranges and export stay free."
- Two plan options as radio rows — **Yearly** (selected by default) and
  **Monthly** — each showing the **price string exactly as the App Store
  returns it** (`displayPrice`), never a hard-coded amount, plus the billing
  period.
- **Subscribe** (primary).
- The renewal terms in full, in readable size: "Payment is charged to your
  Apple Account. The subscription renews automatically at the price shown until
  you cancel, which you can do at any time in your App Store account settings,
  at least 24 hours before the end of the current period."
- **Restore purchases** · **Terms of use** · **Privacy policy**.

Outcomes, shown in a glass card (tap to dismiss). The wording never tells
someone who may have paid to buy again:

| Outcome | Copy |
| --- | --- |
| Entitled | "You are on Pro. Thank you." |
| Confirmed by Apple, not yet by us | "We could not confirm the purchase yet. You have not lost it: we will keep trying." |
| Waiting for approval (Ask to Buy) | "Your payment is waiting for approval. Pro switches on as soon as it clears." |
| Belongs to another bbiom account | "This Apple subscription already belongs to a different bbiom account. Sign in to that account to use it." |
| Nothing to restore | "No earlier purchase was found for this Apple Account." |
| Store unreachable | "The App Store is not reachable right now. Please try again in a moment." |
| Cancelled by the person | Nothing. |

When the account is already Pro the plan options are replaced by one sentence
saying where it is managed.

**Where the paywall is offered:** Settings › See Pro; when a Free limit is hit
(§6, §9); the Doctor summary row. Nowhere else, and never on launch.

## 11. Doctor summary — `summary` · To build (Pro)

**Job:** one page to hand over or send before an appointment.

Port from: `src/app/app/summary/page.tsx`.

- Window control: 6M / 1Y / 3Y / All (default 1Y).
- Kicker "Doctor summary"; title "{name}'s results, on one page"; a line with
  marker count, latest test date and window.
- **Flagged for discussion**: markers whose latest result in the window is out
  of range or borderline — name, value + unit, status.
- **All results in this window**: marker, latest value + unit, date, reference,
  status (shape + words).
- Primary button **Share or print**. Build an HTML document of the same content
  (system font, black on white, no colour except the status shapes, the
  disclaimer as footer), then `expo-print` → `printToFileAsync` → `expo-sharing`
  for the share sheet (which includes Print, Mail, Files, AirDrop).
- The file is created on the device and never uploaded.
- Gating: read `useEntitlement()`; if not Pro, show the paywall instead of the
  screen. This is a convenience feature computed from data the person can
  already read, so the gate is in the app; nothing sensitive depends on it.

## 12. States every screen must handle

Use `QueryState` from `components/ui/primitives.tsx` so these are uniform.

| State | Rule |
| --- | --- |
| Loading with cache | Show the cache immediately; refresh quietly |
| Loading without cache | One centered spinner; no skeletons |
| Empty | A sentence that says what will appear here, and the action that fills it |
| Error | What failed, in plain words, and **Try again**. Never a raw error string. |
| Offline | Reading works from cache. A write says it needs a connection and keeps the input. |
| Limit reached | What the limit is, that existing data is safe, one offer of Pro |

## 13. Accessibility

Required, not optional — part of the audience has poor eyesight or uses
VoiceOver, and App Review tests it.

- **Dynamic Type.** All text uses the styles in `theme/tokens.ts` and scales.
  Layouts must survive the largest non-accessibility size: let rows wrap; never
  set a fixed height on a text container. Cap only where a row would otherwise
  break (`maxFontSizeMultiplier={1.3}` on chips and buttons).
- **VoiceOver.** Every control has a role and a label. A marker card or row is
  one element: "LDL Cholesterol, 94 mg/dL, borderline". Decorative art and
  charts' internals are hidden; the chart has one summarising label and the
  history list carries the detail.
- **Never colour alone.** Status always has its shape and its word.
- **Contrast.** Ink on paper and white on the green of the art are both above
  4.5:1. White text is never placed on the orange part of a painting.
- **Reduce Motion.** No animation in v1 carries meaning; the chart does not
  animate on entry on iOS.
- **Targets.** 44×44pt minimum, including chips and the time-window control
  (use `hitSlop`).

## 14. Words

- Sentence case everywhere. No exclamation marks. No "Oops", "Uh oh", "Hooray".
- Buttons say what they do: "Save test", "Email me a code", "Delete everything".
- Numbers: the value, a thin space, the unit. Ranges with an en dash:
  `70–99`. One-sided ranges in words: "under 100", "over 40".
- Dates: `18 Sep 2026`. Relative time only as a supplement ("2 months ago").
- The disclaimer, verbatim, wherever it appears: "This app tracks values you
  enter; it does not provide medical advice. Reference ranges vary by lab and
  individual. Discuss results with your healthcare provider."
